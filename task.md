# Тестовое задание: Hello World API с кешированием

## 1. Цель задания

Разработать простое веб-приложение, демонстрирующее навыки работы с:

- FastAPI;
- PostgreSQL;
- Redis;
- SQLAlchemy и asyncpg;
- Alembic;
- Docker Compose;
- асинхронным Python-кодом;
- cookie-сессиями;
- кешированием данных.

Приложение должно возвращать приветственную фразу, получая её из PostgreSQL при первом запросе и из Redis при последующих запросах в рамках одной сессии.

---

## 2. Функциональные требования

### 2.1. Эндпоинт

Реализовать эндпоинт:

```http
GET /hello
```

Успешный ответ:

```text
Hello, World!
```

Фраза не должна быть захардкожена в обработчике запроса. Она должна храниться в PostgreSQL.

Допускается возвращать ответ в формате `text/plain` или JSON:

```json
{
  "message": "Hello, World!"
}
```

---

### 2.2. Логика получения данных

При обработке запроса необходимо реализовать следующий алгоритм:

1. Проверить наличие cookie `session_id`.
2. Если cookie отсутствует:
   - сгенерировать новый уникальный идентификатор сессии;
   - установить cookie `session_id` в ответе.
3. Сформировать ключ Redis:

```text
session:{session_id}:hello
```

Например:

```text
session:8b6f5a8d-6b4f-4a5f-9fb9-2cb0c2dc0e22:hello
```

4. Проверить наличие значения по этому ключу в Redis.
5. Если значение найдено:
   - вернуть его из Redis;
   - не выполнять запрос к PostgreSQL.
6. Если значение не найдено:
   - получить приветственную фразу из таблицы `greetings` в PostgreSQL;
   - сохранить её в Redis;
   - установить TTL для Redis-ключа;
   - вернуть фразу клиенту.

---

### 2.3. Кеширование

Для каждой пользовательской сессии должен использоваться отдельный Redis-ключ:

```text
session:{session_id}:hello
```

TTL кеша должен задаваться через переменную окружения:

```env
CACHE_TTL=60
```

Значение TTL указывается в секундах.

Пример:

```text
CACHE_TTL=60
```

означает, что значение хранится в Redis 60 секунд.

После истечения TTL следующий запрос должен снова получить значение из PostgreSQL и обновить кеш.

---

### 2.4. Cookie сессии

Использовать cookie:

```text
session_id
```

Требования:

- cookie должна создаваться автоматически, если клиент не передал её;
- значение cookie должно быть уникальным;
- рекомендуется использовать UUID;
- повторные запросы с одной и той же cookie должны обращаться к одному кешу;
- новая cookie должна приводить к использованию нового Redis-ключа.

Пример заголовка ответа:

```http
Set-Cookie: session_id=8b6f5a8d-6b4f-4a5f-9fb9-2cb0c2dc0e22
```

## 3. Требования к базе данных

### 3.1. Таблица `greetings`

Необходимо создать таблицу:

```sql
CREATE TABLE greetings (
    id SERIAL PRIMARY KEY,
    message VARCHAR(255) NOT NULL,
    created_at TIMESTAMP NOT NULL
);
```

Рекомендуемая SQLAlchemy-модель:

```python
class Greeting(Base):
    __tablename__ = "greetings"

    id: Mapped[int] = mapped_column(
        Integer,
        primary_key=True,
        autoincrement=True,
    )

    message: Mapped[str] = mapped_column(
        String(255),
        nullable=False,
    )

    created_at: Mapped[datetime] = mapped_column(
        DateTime,
        nullable=False,
        server_default=func.now(),
    )
```

---

### 3.2. Начальные данные

В рамках Alembic-миграции необходимо добавить начальную запись:

```text
Hello, World!
```

Миграция должна выполнять:

1. создание таблицы `greetings`;
2. добавление начальной записи;
3. удаление таблицы при откате миграции.

Пример ожидаемых данных:

| id | message | created_at |
|---:|---|---|
| 1 | Hello, World! | дата создания записи |

Сид должен быть реализован как data migration, а не отдельным ручным SQL-скриптом.

## 5. Требования к Docker Compose

Файл:

```text
docker-compose.yml
```

должен содержать следующие сервисы:

### 5.1. Сервис `app`

Назначение:

- запуск FastAPI-приложения;
- запуск Uvicorn;
- работа в dev-режиме;
- автоматическая перезагрузка при изменении исходного кода.

Пример команды запуска:

```bash
uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload
```

Исходный код должен монтироваться в контейнер:

```yaml
volumes:
  - ./app:/app/app
```

или с использованием другой эквивалентной схемы монтирования.

---

### 5.2. Сервис `db`

Назначение:

- запуск PostgreSQL 16;
- хранение данных приложения.

Необходимо:

- использовать volume для сохранения данных;
- передавать настройки через переменные окружения;
- добавить healthcheck PostgreSQL.

---

### 5.3. Сервис `redis`

Назначение:

- запуск Redis 7;
- хранение кеша приложения.

Необходимо:

- добавить healthcheck Redis;
- использовать настройки подключения из переменных окружения.

---

### 5.4. Сервис `migrations`

Назначение:

- выполнение миграций перед запуском приложения.

Команда запуска:

```bash
alembic upgrade head
```

Сервис должен запускаться после готовности PostgreSQL.

Пример:

```yaml
migrations:
  build: .
  command: alembic upgrade head
  depends_on:
    db:
      condition: service_healthy
```

---

### 5.5. Зависимости сервиса `app`

Приложение должно запускаться только после успешного завершения миграций.

Рекомендуемый вариант:

```yaml
app:
  depends_on:
    db:
      condition: service_healthy
    redis:
      condition: service_healthy
    migrations:
      condition: service_completed_successfully
```

Таким образом:

- PostgreSQL должен пройти healthcheck;
- Redis должен пройти healthcheck;
- миграции должны завершиться успешно;
- только после этого запускается FastAPI-приложение.


Необходимо:

- получать настройки из переменных окружения;
- использовать операции `get` и `set`;

Пример логики сохранения:

```python
await redis_client.set(
    key,
    message,
    ex=cache_ttl,
)
```

## 11. Поведение API

### Первый запрос без cookie

Запрос:

```http
GET /hello
```

Ожидаемое поведение:

1. генерируется `session_id`;
2. устанавливается cookie;
3. выполняется запрос к PostgreSQL;
4. результат сохраняется в Redis;
5. клиент получает приветственную фразу.

Пример ответа:

```http
HTTP/1.1 200 OK
Content-Type: text/plain; charset=utf-8
Set-Cookie: session_id=<uuid>
```

```text
Hello, World!
```

---

### Повторный запрос с той же cookie

Запрос:

```http
GET /hello
Cookie: session_id=<uuid>
```

Ожидаемое поведение:

1. используется переданный `session_id`;
2. выполняется проверка Redis;
3. значение возвращается из Redis;
4. PostgreSQL не вызывается.

---

### Запрос после истечения TTL

После истечения времени кеширования:

1. Redis не возвращает значение;
2. приложение получает фразу из PostgreSQL;
3. значение снова сохраняется в Redis;
4. TTL устанавливается заново.

---

## 12. Обработка ошибок

Необходимо предусмотреть базовую обработку следующих ситуаций:

- PostgreSQL временно недоступен;
- Redis временно недоступен;
- в таблице `greetings` отсутствуют записи;
- некорректное значение `CACHE_TTL`;
- ошибка подключения к базе данных;
- ошибка выполнения Redis-команды.

Рекомендуемое поведение при недоступности Redis:

- приложение может продолжить работу, обращаясь к PostgreSQL;
- ошибка кеша не должна приводить к потере данных;
- в логах должна быть отражена причина ошибки.

Рекомендуемое поведение при отсутствии приветствия в БД:

```http
HTTP/1.1 404 Not Found
```

или другой понятный ответ с описанием ошибки.
